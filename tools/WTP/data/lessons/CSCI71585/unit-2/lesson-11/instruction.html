Tutorial

In this final lesson, you will bring together everything from this unit to build a complete web page from scratch, then check it with the same tool professional developers use to find mistakes in their HTML.

Unlike the previous lessons, there are no step-by-step instructions for the build. Instead, you have a brief and a checklist. If you are unsure how to do something, look back at the relevant lesson: the instructions are designed to be used as a reference.


The Brief

A local group is running a one-day Beginners' Web Workshop, and they need a single web page for it. The page must let visitors find out what the workshop is, when and where it is, see the day's schedule, and register a place.

You can make up the details, such as the date, venue and speakers. The page should include the following.


The Document

  • A doctype, a lang attribute and a character encoding.
  • A meaningful <title>.

Page Structure (Lessons 8 and 9)

  • A <header> containing the workshop's name and a <nav>.
  • A <main> containing the sections below, each in its own <section> with an id.
  • A <footer> containing a copyright notice that uses a character entity.
  • No <div> elements, unless no semantic element fits.

Navigation (Lessons 3 and 5)

  • A list of fragment links in the <nav>, one for each section.
  • A Back to top link in the footer.

About the Workshop (Lessons 2, 4 and 5)

  • At least two paragraphs describing the workshop.
  • The date in a <time> element with a datetime attribute.
  • At least one use each of <strong> and <em>, used for their meaning.
  • An abbreviation (such as HTML or CSS) in an <abbr> with a title.
  • A link to an external website, such as https://developer.mozilla.org, opening in a new tab.

The Venue (Lessons 2, 3 and 6)

  • An image of the venue in a <figure> with a <figcaption>. Use https://placehold.co/600x400?text=Venue as the src, with suitable alt text, width and height.
  • The venue address, using <br> for its line breaks.
  • An ordered list of directions to the venue from the nearest station.
  • An unordered list of things to bring on the day.

Schedule (Lesson 7)

  • A table of the day's sessions with at least four rows, with columns for the time, the session and the speaker.
  • A <caption>, a <thead>, a <tbody>, and scope on every header cell.

Speakers (Lesson 9)

  • An <aside> introducing one or more speakers.

Register (Lesson 10)

  • A form with required fields for the user's name and email address.
  • A dropdown to choose a morning or afternoon session.
  • A fieldset of radio buttons asking about the user's experience level, and a fieldset of checkboxes asking which topics interest them.
  • A submit button.
  • A properly connected label for every control.

Plan Before You Build

Before writing any code, sketch the outline of your page, either on paper or as comments in the editor. A plan like the one below makes the build far quicker, and helps you get the nesting right first time:

header
    h1, nav
main
    section#about     h2, p, p
    section#venue     h2, figure, p, ol, ul
    section#schedule  h2, table
    aside             h2, p
    section#register  h2, form
footer
    p

Here, section#about is shorthand for a <section> with an id of about. You will see this notation again in CSS.

💡 Tip: Build the page in stages, and check the preview after each one: first the document structure, then the header and footer, then one section at a time. Fixing a mistake straight after you make it is much easier than finding it later in a long page.

Validating Your HTML

As you saw in Lesson 1, browsers hide your mistakes by guessing what you meant. A page can look perfect while containing errors that cause problems for screen readers, search engines, and your CSS and JavaScript later. A validator is a tool that checks your HTML against the rules of the language and lists every error it finds.

The standard tool is the W3C Markup Validation Service, run by the World Wide Web Consortium. It is free and can check HTML pasted straight into it.

Try It

  1. When your page is complete, select all of your code in the editor and copy it.
  2. Open the W3C validator's Validate by Direct Input page in a new tab.
  3. Paste your code into the box and click Check.
  4. If it shows "Document checking completed. No errors or warnings to show.", your HTML is valid. Otherwise, work through the messages as described below until it is.

Reading Validator Messages

The validator shows two kinds of message:

  • Errors break the rules of HTML, and must be fixed.
  • Warnings are not strictly wrong, but often point to a problem, such as a <section> without a heading. Read each one and decide whether it needs fixing.

Each message gives a line number, a description and the code it refers to. The line numbers match the line numbers in the editor.

💡 Tip: Fix errors from the top down, and check again after fixing each one. A single early mistake, such as a missing closing tag, can confuse the validator about everything after it and produce a long list of errors. Fixing the first one often makes many of the others disappear.

Try It: Break It on Purpose

Learning to recognise common errors makes them much quicker to fix in future. Make each change below, validate your page, read the message, then undo the change:

  1. Delete the alt attribute from your image.
  2. Give two different elements the same id.
  3. Put a <ul> inside a <p>.
  4. Delete the closing tag of one of your sections.

Notice how the first three each produce one clear error, but the missing closing tag may produce several, some of them pointing at lines that are actually correct.


Check Your Page

Your page is complete when:

  • Every item in the brief is included.
  • The heading outline has one <h1> and no skipped levels.
  • Every navigation link jumps to the right section.
  • Every form control has a working label.
  • The W3C validator reports no errors.

Unit Summary

In this unit, you have learned to:

  • Write a valid HTML document, with a doctype, lang attribute, character encoding and title.
  • Mark up text with headings, paragraphs, lists, formatting elements and character entities.
  • Nest elements correctly, and understand block and inline elements.
  • Use attributes, write relative and absolute URLs, and create links.
  • Add images and media with accessible alternatives.
  • Present data in accessible tables.
  • Structure a page with semantic elements, using <div> and <span> only where no semantic element fits.
  • Build accessible forms.
  • Check your HTML with a validator.
